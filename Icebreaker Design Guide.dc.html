Design guide

Icebreaker — Frozen-concept redesign

A reskin brief for UKC Social: same product, mapped onto a frost/ice visual language with Frozen's cast standing in as mock profiles.

Guiding prompt

"Redesign the UKC Social app around a Frozen / Icebreaker concept. Keep every existing screen and flow (onboarding, home, meal matching, group reveal, chat, people directory, rides), but reskin it in a deep frost-navy palette with a single icy-cyan accent. Replace every example name, workplace, job title, and location in the mock data with a Frozen-universe reference — characters, guilds, and places from the film — so the world-building is consistent screen to screen. Alongside the reskin, fix the real UX gaps found by reading the app's own code (not just the visuals): collect a contact and bio during onboarding instead of leaving them for later, persist flight info to the same store Rides reads from, show the table-reveal time on the join sheet, and add a resend option to the "check your email" screen. Add a first onboarding step where the attendee picks which event they're at (with a "none of these" option) and the date range they're staying, so matching only considers people actually there at the same time. Mentor–mentee 1:1 matching is descoped for now — it isn't wired into the real product yet and isn't the priority; put the saved effort into fixing meal matching itself. Add a stay-window feature to People: show each person's arrival/departure relative to the viewer ("Arriving early," "Staying late," "Here the same dates as you") with filter chips, and let anyone with an overlapping stay send a light "Say hi" request — full contacts still stay locked until a real shared table or ride, but the ask itself is no longer gated on that. Re-walking the flow with this in place surfaces two more real gaps to log for implementation: the event picker isn't wired to any schema column, so different-event attendees could still be seated together; and the join sheet doesn't check a slot's date against the signer's stay window, so someone can join a dinner they'll have already left before.

A second, screen-by-screen walkthrough of the mock itself (not the backend) caught three presentation issues, now fixed: no screen showed the bottom tab bar, so the mock read as disconnected screens rather than one app — added a reskinned tab bar to Home, People, and Rides with the active tab marked. The Contact & bio screen's bio field looked identical to an unfilled placeholder despite representing filled content, while the optional LinkedIn field wasn't visually distinguished from it — bio is now shown filled, LinkedIn now reads as a dashed, italic empty state so it's unambiguous which fields still need input.

Keep copy and layout logic close to the real product; only the visual identity, the added UX fixes, and the mock content change. Every fix named here must also be logged in the guide's code-level table (file, issue, fix) so it's directly actionable by whoever implements it in the real codebase — not just a mock-only change. Matching must run as two explicit stages, in order: first a hard schedule filter (event + overlapping stay dates — someone gone before a dinner happens isn't eligible for it, full stop), then interest-based scoring/packing only among whoever passes that filter. Interest fit never overrides a schedule conflict."

UX fixes reflected in this mock

Found by reading the app's actual code (routes, components, `docs/UX-GAP-AUDIT.md`), not by re-guessing from the old audit — most of that doc's items are already fixed in code. These four are the ones still open:

  1. Contact & bio never collected in onboarding — StepBasics.tsx only asks for photo/name/school/position. Added as a step so tablemates aren't shown "no contacts yet."
  2. Flight info persisted nowhere real — StepPlans.tsx only writes to localStorage["ukc-flight"]; /rides reads the separate Supabase flights table. Rides screen now flags the sync explicitly.
  3. Join sheet doesn't say when tables are revealed — JoinSheet.tsx shows slot time/area but never join_deadline. Added to the sheet.
  4. "Check your email" has no resend — login/page.tsx's sent-state only offers "back to sign in." Added Resend + change-email.

Matching algorithm — code-level fixes needed

Traced the actual matching path end to end (lib/matching.ts, lib/mentorMatch.ts, lib/groupName.ts, app/actions/admin.ts, app/mentor/page.tsx, lib/rides.ts). These aren't visual — they need backend work, but the mock now signals a couple of them (the "Matched by shared interest" badge, the mentor opt-in note).

File Issue Fix direction
lib/matching.ts + admin.ts (ordering) Pipeline order matters. Schedule fit (event + stay-date overlap) is a hard constraint — someone gone before a dinner happens can't be seated at it, no matter how well interests match. Interest/topic scoring is a soft, secondary rank within whoever passes that filter. Today there's no schedule filter at all (see the event_id row below), so this ordering isn't implemented yet in either direction. Build as two explicit stages in runMatching: (1) filter signups to the slot's date, event, and each signer's stay window — this determines who's even eligible; (2) run interest-based scoring/packing only on that eligible set. Never let a strong interest match override a schedule conflict.
lib/matching.ts Separately: when total headcount ≤ 6 (most real dinner slots), matchSlot() skips the LLM entirely and calls roundRobinGroups(), which bin-packs by party size only — no interests, school, or position considered. The core "seated by what you work on" promise never fires for the common case. Run the interest-aware LLM (or a lightweight local scoring pass) even for single-table slots; reserve pure round-robin for genuine API failure only.
lib/matching.ts On LLM failure or a failed validateAssignment (2 retries), the whole slot falls back to the same interest-blind packer — no partial reuse of a valid subset. Keep any valid groups from a failed attempt; only re-pack the invalid ones.
lib/groupName.ts + admin.ts A round-robin table still gets a flavorful bank name (e.g. "Model Citizens") while its rationale stays the hardcoded "Grouped to keep tables even." — name and reasoning contradict each other to the user. Either only draw a topical name when the table was actually interest-matched, or write an honest rationale for the balance-only path (mock's new badge models this).
lib/mentorMatch.ts + app/mentor/ Descoped for now — fully built (scoring, greedy 1:1, group fusion) but only exercised by scripts/match-report.ts against synthetic data; never wired to a real admin action. Not a current priority vs. fixing meal matching. Leave as-is. If revisited later: add a runMentorMatching action mirroring admin.ts, fix the capacity>1 double-membership bug in suggestGroups(), and stop roleFromPosition() defaulting a blank position to "mentor."
lib/rides.ts + new onboarding step EVENT_OFFSET = "-04:00" and EVENT_AIRPORT are hardcoded for one event/timezone. Separately, the new "which event / stay dates" onboarding step isn't read by matching.ts or rides.ts at all yet — it's UI only in this mock. Make offset/airport per-event config; filter both dinner and ride candidates to overlapping stay-date ranges before matching runs.
components/PeopleBrowser.tsx + can_see_contact() New feature, not yet in code. No notion of stay-date overlap exists in the People directory, and there's no lightweight way to reach out before a shared table/ride — can_see_contact() is the only gate, and it's all-or-nothing. Add stay-window fields to the profile query; compute an overlap badge client-side. Add a low-stakes "connection request" (new table, e.g. hi_requests) separate from shares_channel() — a request notifies the recipient but does NOT itself unlock contacts, so RLS on contact fields stays unchanged.
supabase/migrations + admin.ts Re-walked the flow with the new Event & stay step in mind: slots/signups/profiles have no event_id or stay-date columns at all. Two people who picked different events (or "None of these") in onboarding could still land in the same signups list and get seated together by runMatching — the event picker is currently cosmetic. This is the schedule-filter data the ordering fix above depends on. Add event_id + stay_start/stay_end to profiles; scope every slot query (meals, rides, people directory) to the viewer's event and use the dates to drive the hard filter in runMatching. "None of these" users should see a reduced, event-agnostic experience (e.g. People only), not join real event slots.
components/JoinSheet.tsx Now that stay dates exist, JoinSheet.tsx still lets anyone join any dinner slot regardless of whether it falls inside their check-in/check-out — someone leaving Aug 6 can join the Aug 8 dinner and get seated at a table they'll never show up to. Compare the slot's date against the signer's stay range before allowing Join; warn or block ("You're leaving before this one — still join?") rather than silently allowing it.

New step: Event & stay (before Interests)

Today onboarding assumes every user is at UKC and staying the full run of the conference — neither is guaranteed. This step asks two things before anything else, so every later match (dinner, ride, person) is scoped to people who are actually around at the same time.

Field Options / input Why it matters
Event Radio cards: UKC 2026, KSEA Conference, None of these Scopes matching to one event's roster; "None of these" keeps the app usable for someone just exploring, without forcing a false pick.
Stay dates Check-in / check-out date pickers A dinner or ride match on day 3 is useless to someone who leaves after day 1 — this keeps every suggestion inside their actual window.

Placed as onboarding step 1 of 4 (progress bar updated accordingly); Interests and Contact/bio shift to steps 2 and 3. Picking "None of these" can later be used to soften copy elsewhere (e.g. skip event-specific venue suggestions), though that's not built into this mock.
